# Follow-up des audits du 6 octobre 2026

**Date de revue :** 2026-10-08  
**Baseline des audits :** `78ae66f6157bd77df1f89cb88c579999ffa7fc9a` (Phase 3B1)  
**Baseline de cette revue :** `507c11b7c0a0eb6912006a79ad8dcdd53abcffd2` (`main` après PR #79)  
**Dernière actualisation :** `0d05959a2ea8198ba596f3f0ba2ccd8f3ca89ce4` (après PR #109 / B-02A)
**Objet :** vérifier si les findings importants des audits architecture/sécurité et adversarial/invariants sont réellement fermés, seulement mitigés, ou encore ouverts.

## Légende

- **RÉGLÉ** : le risque décrit par le finding est mécaniquement fermé dans l'état courant.
- **PARTIEL** : une mitigation importante existe, mais le contrat complet proposé par l'audit n'est pas encore atteint.
- **OUVERT** : le finding reste applicable.
- **RÉGLÉ (priorité)** : le problème de roadmap/priorisation est corrigé, même si le chantier technique associé continue.

## Résumé

Les principaux bloqueurs multi-session de l'ancien baseline ont fortement avancé : admission/revoke, expiry/reap, bounded task leases, canonical lifecycle provisioning, bounded termination, CPU governance, executable identity et isolation cross-session sont implémentés et validés. PR #99 / Phase 3D ajoute une preuve adversariale composée A/B/C : cross-session lease/JobId denial, pression locale bornée, revoke/reap owner-scoped et réutilisation sûre de capacité pendant qu'une session étrangère reste active.

Le principal groupe de risques encore ouvert concerne désormais l'**autonomie large / publique** plutôt que le socle multi-session interne : ResourceGovernor machine complet (désormais surtout headroom physique/emergency reserve, classes de tâches et I/O éventuel), ToolProfiles/ApprovalBroker, read/search scopes, runner commun, environnement classifié, extension de la preuve réseau et plusieurs hardenings transport/supply-chain.

Le modèle high-risk a également progressé au-delà du deny global initial : C5A-C5G réadmettent sélectivement un `node.exe` exact, operator-owned, via AppContainer/helper, avec `process_count=1`, sans réseau ni process workspace-read implicite. Le vrai ChatGPT Desktop a exécuté `node --version` avec approbation explicite et a retourné `v22.15.1`. Cette preuve ne généralise pas l'admission à Python/Java/Cargo/rustc ni aux builds/tests de dépôt.

# Audit n°1 — findings A

## A-01 — Race admission / révocation — **RÉGLÉ**

Phase 3B2 (PR #52) a introduit la barrière d'admission de session : la révocation ferme les nouvelles admissions et attend les effets déjà admis avant lease/job cleanup. Phase 3B3 réutilise ce chemin pour l'expiry/reap.

## A-02 — ResourceGovernor global machine — **PARTIEL**

Depuis l'audit :

- limites globales + par session sur sessions, jobs, process records et output RAM ;
- réservation CPU globale/per-session + hard cap CPU Job Object par process job ;
- Phase 3D prouve la composition cross-session sous pression/revoke/reap ;
- Phase 3E1 / PR #101 (`097b6a37`, exact head `b8447deb`, CI #406/#407) ajoute une réservation **déclarée** de mémoire process : 16 GiB bridge-wide, 8 GiB par session, plafond par job 8 GiB inchangé ; `Running` et `TerminationUncertain` restent comptés, un terminal prouvé libère sa réservation ;
- Windows conserve en parallèle `JOB_OBJECT_LIMIT_JOB_MEMORY` par job, et la création/configuration du Job Object précède désormais la publication du JobRecord ;
- Phase 3E2A / PR #103 (`e2b37be0`, exact head `3c765d9e`, CI #410/#411) ajoute une observation Windows validée de la mémoire physique totale/disponible via `GlobalMemoryStatusEx` ;
- Phase 3E2B / PR #105 (`aaaf4e17`, exact head `9cb0516f`, CI #414/#415) consomme cette observation sous le verrou d'admission : réserve effective `max(1 GiB, 10% RAM physique totale)` + réservations déclarées 3E1 actives/incertaines + budget du nouveau job, avec télémétrie invalide/indisponible fail-closed et codes MCP distincts ;
- Phase 3E3 / PR #107 (`826f8cb3`, final head `203d729c`, CI #421/#422) ajoute `WorkloadClass::{Standard, Heavy}` application-owned et borne les process lourds à 2 slots globaux / 1 par session. Les jobs `Running` et `TerminationUncertain` conservent leur slot, un terminal prouvé le libère, et MCP ne peut ni fournir ni dégrader la classe.

Toujours manquant par rapport au finding original :

- éventuel budget I/O / feedback de pression mémoire plus riche.

Les deux trous mémoire principaux et le trou de concurrence heavy sont maintenant mécaniquement couverts : 3E1 borne les réservations déclarées globales/par session, 3E2B refuse une nouvelle admission Windows qui ne conserverait pas l'emergency headroom défini, et 3E3 borne séparément les workloads lourds. A-02 reste **PARTIEL** uniquement parce qu'aucun budget I/O / feedback de pression plus riche n'est encore implémenté. Ce reliquat est explicitement séparé et n'empêche pas de passer au finding prioritaire suivant ; 3E2B reste un garde-fou ponctuel d'admission et ne prétend pas contrôler les allocations ultérieures de processus étrangers.

## A-03 — Pas de vrai contrôle CPU — **RÉGLÉ**

Phase 3C2 (PR #57) : défauts 25 % par job, 75 % aggregate Optic et 50 % par session ; Windows applique `JOB_OBJECT_CPU_RATE_CONTROL_HARD_CAP` avant resume.

## A-04 — Identité executable liée surtout au chemin — **RÉGLÉ pour le risque de remplacement ; PARTIEL pour ToolRegistry**

Phase 3C3A (PR #59) capture une identité BLAKE3 bornée. Sur Windows, le lease conserve un handle qui empêche write/delete/rename replacement et l'identité est revalidée lors des usages actifs.

Le risque concret « même chemin, binaire remplacé » est fermé sur Windows pour les leases actifs. En revanche, signer/version/provenance/trust mode et registre d'outils complet restent futurs.

## A-05 — Reads/cwd encore canonicalize-then-use — **OUVERT / PARTIEL**

Les mutations Windows et les grants AppContainer exact-file ont des bindings handle-first beaucoup plus forts.

Mais le `BoundedFileSystem::read()` général résout/canonicalise puis ouvre encore par path, et `ProcessManager::resolve_cwd()` canonicalise puis transmet le path au spawn. Le hardening handle-first générique proposé par l'audit reste donc pertinent.

## A-06 — TTL session fixe 30 minutes / renouvellement — **OUVERT**

L'expiration est désormais correctement orchestrée et reaped, mais le TTL initial reste 30 minutes et il n'existe pas encore de protocole public/application-owned de renouvellement.

## A-07 — Pas de vrai ApprovalBroker — **OUVERT**

`PolicyDecision::RequireApproval` existe mais Optic ne possède pas encore de broker local matérialisant un grant exact action/target/resource/expiry. Le prompt-gating du packaging ne remplace pas ce composant.

## A-08 — Restricted / Allowed / Full comme presets UX — **OUVERT**

Pas encore de `AccessPreset`/policy compiler persistent. À conserver comme couche UX compilant capabilities/scopes/leases/règles, jamais comme bypass.

## A-09 — Read/Search scopes pour recherche PC — **OUVERT**

Le runtime possède `FileSearch`, mais pas les scopes distincts proposés (`SearchMetadataScope`, `ReadContentScope`, `ReadSensitiveScope`). Aucune recherche machine globale ne doit être exposée avant cette séparation.

## A-10 — HardenedCommandRunner commun — **OUVERT**

Process runtime, Git read et Git integration conservent des chemins d'exécution distincts. `GitReadService` construit encore directement `std::process::Command`. Le runner commun reste pertinent.

## A-11 — `spawn_blocking` read/list non annulable — **OUVERT**

Les reads/list MCP sont toujours exécutés via `spawn_blocking` sous timeout. Le timeout peut rendre la main sans annuler un blocking task déjà démarré. Le problème est moins critique que pour une mutation mais reste réel pour des opérations pathologiques/stuck I/O.

## A-12 — Configuration persistante versionnée — **OUVERT**

L'autorité reste principalement CLI/startup et packaging. Aucun `OpticConfig v1` persistant/versionné avec policy-epoch migration n'existe encore.

# Audit n°2 — findings B

## B-01 — `ProcessRun` confused deputy — **PARTIEL, profil Node sélectif prouvé**

Depuis l'audit :

- Phase 3C3B classe `FixedTool`, `Interpreter`, `RepositoryCode` ;
- C5A-C5C exigent un marqueur `ProcessIsolationEligible { executable, class }` exact en plus de l'autorité d'exécutable ;
- C5D-C5F distribuent le helper et n'autorisent en production que l'opt-in exact Windows `node.exe` déjà classé `Interpreter`, avec `process_count=1` ;
- C5G a validé cette voie depuis un vrai ChatGPT Desktop : approbation explicite, `node --version`, `network=false`, aucun process workspace-read grant, résultat `v22.15.1` / exit 0.

Le finding reste **partiel** car un `ToolProfile` complet (subcommand/args/cwd/fs/network/env/resource/approval) n'existe pas encore et les autres classes/profils high-risk ne sont pas réadmis par analogie. La voie Node sélectionnée n'est plus seulement mitigée : elle est mécaniquement prouvée, mais elle ne ferme pas le modèle générique de confused deputy.

## B-02 — `network=false` n'est pas une barrière OS — **PARTIEL, faille `FixedTool` caractérisée**

PR #85 (`bb649833`, exact head `6fcc25d1`) ferme un premier gate mécanique pour le chemin high-risk AppContainer : un Node déjà prouvé compatible est lancé via le vrai helper dans un AppContainer sans capability réseau ; le script atteint `NETWORK_ATTEMPT`, ne se connecte jamais à un listener TCP `127.0.0.1`, et le listener n'accepte aucune connexion du sandbox. PR CI #365 et post-merge `main` CI #366 sont verts.

B-02A / PR #109 (`0d05959a`, exact head `4a96ff09`, CI #426/#427) caractérise désormais séparément le chemin direct `FixedTool`. Le premier essai à environnement vide a été rejeté comme preuve car Winsock échouait plus tôt avec l'erreur 10106. Avec uniquement `SystemRoot` restauré via l'allowlist serveur existante, le child atteint `FIXED_TOOL_NETWORK_ATTEMPT`, puis `FIXED_TOOL_NETWORK_CONNECTED`, sort avec code 0 et le listener hôte accepte réellement la connexion TCP/IPv4 loopback. Le finding n'est donc plus hypothétique pour ce chemin : `network=false` n'empêche pas actuellement ce socket.

Le finding reste **partiel** : B-02B doit ajouter un confinement OS véridique au chemin direct `FixedTool` avant de pouvoir considérer `network=false` comme une garantie runtime sur ce chemin. La preuve actuelle ne couvre toujours pas UDP, IPv6, toutes les destinations Internet/intranet, les autres familles d'adresses, les machines où une exemption loopback AppContainer aurait été configurée extérieurement, ni tous les futurs chemins d'exécution. `network=true` reste fail-closed et aucune `NetworkAccess` authority n'est provisionnée.
## B-03 — Expiration naturelle non coordonnée — **RÉGLÉ**

Phase 3B3 : supervisor 5 s, `inactive_handles()` puis `SessionLifecycleManager::reap_inactive()`, qui réutilise revoke/admission barrier/job cancellation/safe reap.

## B-04 — Timeout/kill pas absolument borné — **RÉGLÉ**

Phase 3C1 (PR #55) : kill + confirmation bornée ; impossibilité de prouver la mort => `TerminationUncertain`, qui conserve ownership/quota et bloque le reap comme état non terminal.

## B-05 — `TaskLeaseRegistry` non borné — **RÉGLÉ**

Phase 3B3 ajoute `max_task_leases` et `max_task_leases_per_session` avec refus fail-closed.

## B-06 — `remove_expired()` footgun — **RÉGLÉ**

Le registre de leases n'expose plus de purge générique expirée. Les removals physiques sont étroites (`remove_revoked`, `remove_session`) et la voie normale passe par le lifecycle/quiescent reap.

## B-07 — Provisioning principal hors LifecycleManager — **RÉGLÉ**

Le startup principal utilise maintenant `SessionLifecycleManager::provision()`.

## B-08 — Schémas MCP non uniformément stricts — **OUVERT**

`GitIntegrateRequest` et le protocole interne du launcher utilisent `deny_unknown_fields`, mais plusieurs requêtes publiques (`ProcessStartRequest`, process read/job, mutation requests, etc.) ne le font toujours pas. L'uniformisation reste une bonne cible hardening.

## B-09 — Mutation 8 MiB vs frame MCP 1 MiB/base64 — **OUVERT**

Les defaults sont encore :

- `max_request_bytes = 1 MiB` ;
- `max_fs_mutation_bytes = 8 MiB` ;
- `fs_write` transporte le contenu en base64 dans la même request.

Le plafond mutation interne n'est donc pas atteignable via une seule frame stdio MCP. Une limite exposée réaliste ou un staging chunké reste à concevoir.

## B-10 — Serializer réponse alloue avant limite — **OUVERT**

`serialize_json_line_bounded()` fait encore `serde_json::to_vec()` puis vérifie la taille. Les réponses métiers sont largement bornées avant ce point, donc risque faible, mais le hardening streaming/counting proposé n'est pas fait.

## B-11 — Frame invalide tue le receive side — **OUVERT / décision locale acceptable**

Le transport stdio marque toujours `receive_failed = true` après une erreur codec et ferme ensuite le receive side. Fail-closed et acceptable pour une connexion locale unique, mais le futur daemon/HTTP multi-client devra isoler ce type d'erreur à la connexion concernée.

## B-12 — Git read environnement moins hermétique — **OUVERT**

`GitReadService` fixe plusieurs variables protectrices mais n'appelle toujours pas `env_clear()`. À harmoniser avec un futur runner/env profile commun.

## B-13 — Build/test exécute du code repo non fiable — **PARTIEL, volontairement bloqué**

Le modèle `ProcessExecutionClass::RepositoryCode` existe, mais aucun profil build/test de dépôt n'est actuellement réadmis. PR #82/#83 ont caractérisé le chemin réel : Cargo direct démarre dans l'AppContainer, tandis que rustc direct conserve une dépendance loader. La réadmission C5E-C5G concerne uniquement un `node.exe` exact classé `Interpreter` et ne vaut pas autorisation de build/test de dépôt. Le finding devient fermé seulement lorsque des builds/tests réellement réadmis auront prouvé filesystem/network/env/resource containment approprié.

## B-14 — Env allowlist peut transporter secrets/injection — **OUVERT**

`ProcessStartRequest` expose encore une liste de noms d'env, vérifiée contre une allowlist opérateur, mais sans `EnvGrant` classifié secret/behavior/tool profile/redaction. Le high-risk helper réduit l'environnement baseline, mais le problème de modèle reste ouvert.

## B-15 — Canonical read observation avant scoped policy — **OUVERT**

Le `fs_read` général reste workspace-safe mais n'a pas encore le futur `ReadTargetObservation` handle/identity nécessaire avant des scopes de recherche/lecture PC fins.

## B-16 — GitHub Actions pin par tag mutable — **OUVERT**

La CI utilise toujours notamment `actions/checkout@v6` et n'épingle pas les actions tierces par SHA complet.

## B-17 — Source de vérité version — **OUVERT**

Workspace Rust = `0.0.1`, plugin ChatGPT = `0.1.4`. Aucun mécanisme automatique unique n'a encore fermé la divergence.

## B-18 — Executable identity au moment de l'usage — **RÉGLÉ sur Windows pour leases actifs**

Phase 3C3A : capture identité + handle pin Windows + revalidation sur `get_active()`. Le scénario de remplacement entre grant et usage est mécaniquement fortement fermé sur Windows.

## B-19 — Sandbox fort trop tard dans la roadmap — **RÉGLÉ pour la priorité et le profil Node sélectionné**

Le chantier a été remonté immédiatement puis mené jusqu'à une preuve produit ciblée : AppContainer identity, captured stdio, helper séparé, ProcessManager routing, exact-file grants, lifecycle/provisioning operator-owned, caractérisation toolchain, preuve TCP-loopback sans capability réseau, marqueur strong-isolation exact, packaging et réadmission sélective de Node. C5G a fermé le chemin réel ChatGPT Desktop -> MCP -> helper/AppContainer -> `node.exe --version` avec approbation explicite.

Cette fermeture concerne le profil Node sélectionné ; elle ne signifie pas que Python/Java/rustc/builds de dépôt ou le chemin direct `FixedTool` héritent automatiquement des mêmes garanties.

# Findings importants encore à traiter avant autonomie large

Priorité recommandée après C5G + Phase 3D + Phase 3E1 + Phase 3E2A + Phase 3E2B + Phase 3E3 :

1. **B-02B** : ajouter un confinement réseau OS véridique au chemin direct `FixedTool`, désormais prouvé capable d'ouvrir le TCP/IPv4 loopback malgré `network=false` ;
2. **A-07 / B-01** : ApprovalBroker exact et ToolProfiles application-owned avant d'élargir l'autonomie process ;
3. **B-13** : ne réadmettre les builds/tests de dépôt qu'après preuve explicite de leurs dépendances filesystem/network/env/resource ;
4. **A-05/B-15/A-09** : modèle read/search handle-first/scopé avant toute recherche PC ;
5. **B-14/A-10/B-12** : env profiles + HardenedCommandRunner commun ;
6. **B-08/B-09/B-10/B-11** : hardening MCP/transport ;
7. **B-16/B-17** : supply-chain/versioning avant release publique ;
8. **A-06/A-12** : renewal + config persistante avant UX produit/multi-session public.

Le reliquat **A-02** (budget I/O / feedback de pression mémoire plus riche) reste séparé et optionnel : il doit être scopé explicitement avant implémentation plutôt que bloquer automatiquement B-02.

## Conclusion

Les deux audits ont été utiles : les findings les plus dangereux sur la **cohérence lifecycle/process** ont réellement provoqué des changements d'architecture. C5G ferme une première réadmission high-risk sélective sur le vrai produit, Phase 3D compose les invariants multi-session A/B/C, Phase 3E1 ferme l'absence de réservation mémoire process agrégée/par-session, Phase 3E2A fournit l'observation mémoire physique hôte, Phase 3E2B ajoute l'emergency headroom d'admission, Phase 3E3 borne les workloads lourds globalement/par session et B-02A transforme le risque réseau `FixedTool` en fait mécanique reproduit. Le socle interne est donc nettement plus mature, mais les audits ne sont pas entièrement soldés : B-02B confinement `FixedTool`, I/O/pressure feedback éventuel, ToolProfiles/approvals, scopes read/search, runner/env commun, hardening transport et supply-chain restent nécessaires avant autonomie publique lourde ou distante.
