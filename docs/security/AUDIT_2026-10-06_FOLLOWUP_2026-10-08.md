# Follow-up des audits du 6 octobre 2026

**Date de revue :** 2026-10-08  
**Baseline des audits :** `78ae66f6157bd77df1f89cb88c579999ffa7fc9a` (Phase 3B1)  
**Baseline de cette revue :** `507c11b7c0a0eb6912006a79ad8dcdd53abcffd2` (`main` après PR #79)  
**Objet :** vérifier si les findings importants des audits architecture/sécurité et adversarial/invariants sont réellement fermés, seulement mitigés, ou encore ouverts.

## Légende

- **RÉGLÉ** : le risque décrit par le finding est mécaniquement fermé dans l'état courant.
- **PARTIEL** : une mitigation importante existe, mais le contrat complet proposé par l'audit n'est pas encore atteint.
- **OUVERT** : le finding reste applicable.
- **RÉGLÉ (priorité)** : le problème de roadmap/priorisation est corrigé, même si le chantier technique associé continue.

## Résumé

Les principaux bloqueurs multi-session de l'ancien baseline ont fortement avancé : admission/revoke, expiry/reap, bounded task leases, canonical lifecycle provisioning, bounded termination, CPU governance et executable identity sont maintenant implémentés et validés en CI.

Le principal groupe de risques encore ouvert concerne désormais l'**autonomie large** plutôt que le socle multi-session : réseau réellement bloqué au niveau OS, ToolProfiles/ApprovalBroker, ResourceGovernor machine complet (notamment RAM/headroom/classes de tâches), read/search scopes, runner commun, environnement classifié, et plusieurs hardenings transport/supply-chain.

La stratégie actuelle `Interpreter` / `RepositoryCode` = **deny-by-default** empêche plusieurs findings ProcessRun d'être exploitables depuis le MCP public aujourd'hui. Cela est une mitigation forte, mais ne doit pas être compté comme une fermeture fonctionnelle tant que les toolchains ne sont pas réadmises sous confinement prouvé.

# Audit n°1 — findings A

## A-01 — Race admission / révocation — **RÉGLÉ**

Phase 3B2 (PR #52) a introduit la barrière d'admission de session : la révocation ferme les nouvelles admissions et attend les effets déjà admis avant lease/job cleanup. Phase 3B3 réutilise ce chemin pour l'expiry/reap.

## A-02 — ResourceGovernor global machine — **PARTIEL**

Depuis l'audit :

- limites globales + par session sur sessions, jobs, process records et output RAM ;
- réservation CPU globale/per-session ;
- hard cap CPU Job Object par process job.

Toujours manquant par rapport au finding original :

- plafond agrégé explicite de mémoire process Optic au niveau machine ;
- réserve OS/emergency headroom ;
- heavy-task slots/classes de tâches ;
- éventuel budget I/O.

`max_process_budget.memory_bytes` reste un plafond **par job**, pas un governor mémoire machine agrégé.

## A-03 — Pas de vrai contrôle CPU — **RÉGLÉ**

Phase 3C2 (PR #57) : défauts 25 % par job, 75 % aggregate Optic et 50 % par session ; Windows applique `JOB_OBJECT_CPU_RATE_CONTROL_HARD_CAP` avant resume.

## A-04 — Identité executable liée surtout au chemin — **RÉGLÉ pour le risque de remplacement ; PARTIEL pour ToolRegistry**

Phase 3C3A (PR #59) capture une identité BLAKE3 bornée. Sur Windows, le lease conserve un handle qui empêche write/delete/rename replacement et l'identité est revalidée lors des usages actifs.

Le risque concret « même chemin, binaire remplacé » est fermé sur Windows pour les leases actifs. En revanche, signer/version/provenance/trust mode et registre d'outils complet restent futurs.

## A-05 — Reads/cwd encore canonicalize-then-use — **OUVERT / PARTIEL**

Les mutations Windows et les grants AppContainer exact-file ont des bindings handle-first beaucoup plus forts.

Mais le `BoundedFileSystem::read()` général résout/canonicalise puis ouvre encore par path, et `ProcessManager::resolve_cwd()` canonicalise puis transmet le path au spawn. Le hardening handle-first générique proposé par l'audit reste donc pertinent.

## A-06 — TTL session fixe 30 minutes / renouvellement — **OUVERT**

L'expiration est désormais correctement orchestrée et reaped, mais le TTL initial reste 30 minutes et il n'existe pas encore de protocole public/application-owned de renouvellement.

## A-07 — Pas de vrai ApprovalBroker — **OUVERT**

`PolicyDecision::RequireApproval` existe mais Optic ne possède pas encore de broker local matérialisant un grant exact action/target/resource/expiry. Le prompt-gating du packaging ne remplace pas ce composant.

## A-08 — Restricted / Allowed / Full comme presets UX — **OUVERT**

Pas encore de `AccessPreset`/policy compiler persistent. À conserver comme couche UX compilant capabilities/scopes/leases/règles, jamais comme bypass.

## A-09 — Read/Search scopes pour recherche PC — **OUVERT**

Le runtime possède `FileSearch`, mais pas les scopes distincts proposés (`SearchMetadataScope`, `ReadContentScope`, `ReadSensitiveScope`). Aucune recherche machine globale ne doit être exposée avant cette séparation.

## A-10 — HardenedCommandRunner commun — **OUVERT**

Process runtime, Git read et Git integration conservent des chemins d'exécution distincts. `GitReadService` construit encore directement `std::process::Command`. Le runner commun reste pertinent.

## A-11 — `spawn_blocking` read/list non annulable — **OUVERT**

Les reads/list MCP sont toujours exécutés via `spawn_blocking` sous timeout. Le timeout peut rendre la main sans annuler un blocking task déjà démarré. Le problème est moins critique que pour une mutation mais reste réel pour des opérations pathologiques/stuck I/O.

## A-12 — Configuration persistante versionnée — **OUVERT**

L'autorité reste principalement CLI/startup et packaging. Aucun `OpticConfig v1` persistant/versionné avec policy-epoch migration n'existe encore.

# Audit n°2 — findings B

## B-01 — `ProcessRun` confused deputy — **PARTIEL, fortement mitigé**

Depuis l'audit :

- Phase 3C3B classe `FixedTool`, `Interpreter`, `RepositoryCode` ;
- Phase 3C3C1 refuse `Interpreter` / `RepositoryCode` dans la policy publique ;
- AppContainer + helper + exact-file grants + provisioning operator-owned ont été construits en tranches suivantes.

Le risque public immédiat est donc fortement réduit. Mais un vrai `ToolProfile` (subcommand/args/cwd/fs/network/env/resource/approval) n'existe pas encore, et la compatibilité toolchain AppContainer n'est pas terminée. Finding non totalement fermé avant réadmission high-risk.

## B-02 — `network=false` n'est pas une barrière OS — **OUVERT**

Toujours vrai pour le runtime général/fixed-tool : le policy/runtime refuse `network=true`, mais `network=false` ne signifie pas qu'un process user-level ne peut techniquement ouvrir un socket. Les docs actuelles évitent correctement de revendiquer le contraire.

Le chemin AppContainer high-risk n'accorde pas de capability réseau, mais le projet n'a pas encore fermé un gate de **network containment proof** et ne doit pas annoncer `network denied by OS` avant cela.

## B-03 — Expiration naturelle non coordonnée — **RÉGLÉ**

Phase 3B3 : supervisor 5 s, `inactive_handles()` puis `SessionLifecycleManager::reap_inactive()`, qui réutilise revoke/admission barrier/job cancellation/safe reap.

## B-04 — Timeout/kill pas absolument borné — **RÉGLÉ**

Phase 3C1 (PR #55) : kill + confirmation bornée ; impossibilité de prouver la mort => `TerminationUncertain`, qui conserve ownership/quota et bloque le reap comme état non terminal.

## B-05 — `TaskLeaseRegistry` non borné — **RÉGLÉ**

Phase 3B3 ajoute `max_task_leases` et `max_task_leases_per_session` avec refus fail-closed.

## B-06 — `remove_expired()` footgun — **RÉGLÉ**

Le registre de leases n'expose plus de purge générique expirée. Les removals physiques sont étroites (`remove_revoked`, `remove_session`) et la voie normale passe par le lifecycle/quiescent reap.

## B-07 — Provisioning principal hors LifecycleManager — **RÉGLÉ**

Le startup principal utilise maintenant `SessionLifecycleManager::provision()`.

## B-08 — Schémas MCP non uniformément stricts — **OUVERT**

`GitIntegrateRequest` et le protocole interne du launcher utilisent `deny_unknown_fields`, mais plusieurs requêtes publiques (`ProcessStartRequest`, process read/job, mutation requests, etc.) ne le font toujours pas. L'uniformisation reste une bonne cible hardening.

## B-09 — Mutation 8 MiB vs frame MCP 1 MiB/base64 — **OUVERT**

Les defaults sont encore :

- `max_request_bytes = 1 MiB` ;
- `max_fs_mutation_bytes = 8 MiB` ;
- `fs_write` transporte le contenu en base64 dans la même request.

Le plafond mutation interne n'est donc pas atteignable via une seule frame stdio MCP. Une limite exposée réaliste ou un staging chunké reste à concevoir.

## B-10 — Serializer réponse alloue avant limite — **OUVERT**

`serialize_json_line_bounded()` fait encore `serde_json::to_vec()` puis vérifie la taille. Les réponses métiers sont largement bornées avant ce point, donc risque faible, mais le hardening streaming/counting proposé n'est pas fait.

## B-11 — Frame invalide tue le receive side — **OUVERT / décision locale acceptable**

Le transport stdio marque toujours `receive_failed = true` après une erreur codec et ferme ensuite le receive side. Fail-closed et acceptable pour une connexion locale unique, mais le futur daemon/HTTP multi-client devra isoler ce type d'erreur à la connexion concernée.

## B-12 — Git read environnement moins hermétique — **OUVERT**

`GitReadService` fixe plusieurs variables protectrices mais n'appelle toujours pas `env_clear()`. À harmoniser avec un futur runner/env profile commun.

## B-13 — Build/test exécute du code repo non fiable — **PARTIEL, volontairement bloqué**

Le modèle `ProcessExecutionClass::RepositoryCode` existe et le MCP public le refuse actuellement. Le chantier AppContainer est précisément la réponse en cours. Le finding devient fermé seulement lorsque des builds/tests réellement réadmis auront prouvé filesystem/network/env/resource containment approprié.

## B-14 — Env allowlist peut transporter secrets/injection — **OUVERT**

`ProcessStartRequest` expose encore une liste de noms d'env, vérifiée contre une allowlist opérateur, mais sans `EnvGrant` classifié secret/behavior/tool profile/redaction. Le high-risk helper réduit l'environnement baseline, mais le problème de modèle reste ouvert.

## B-15 — Canonical read observation avant scoped policy — **OUVERT**

Le `fs_read` général reste workspace-safe mais n'a pas encore le futur `ReadTargetObservation` handle/identity nécessaire avant des scopes de recherche/lecture PC fins.

## B-16 — GitHub Actions pin par tag mutable — **OUVERT**

La CI utilise toujours notamment `actions/checkout@v6` et n'épingle pas les actions tierces par SHA complet.

## B-17 — Source de vérité version — **OUVERT**

Workspace Rust = `0.0.1`, plugin ChatGPT = `0.1.4`. Aucun mécanisme automatique unique n'a encore fermé la divergence.

## B-18 — Executable identity au moment de l'usage — **RÉGLÉ sur Windows pour leases actifs**

Phase 3C3A : capture identité + handle pin Windows + revalidation sur `get_active()`. Le scénario de remplacement entre grant et usage est mécaniquement fortement fermé sur Windows.

## B-19 — Sandbox fort trop tard dans la roadmap — **RÉGLÉ (priorité), implémentation encore en cours**

Le chantier a été remonté immédiatement : AppContainer identity, captured stdio, helper séparé, ProcessManager routing, exact-file read grant, grant lifecycle et operator-owned read provisioning sont maintenant implémentés. La prochaine étape est la compatibilité toolchain, puis seulement une éventuelle réadmission sélective.

# Findings importants encore à traiter avant autonomie large

Priorité recommandée après le gate toolchain actuel :

1. **B-02** : prouver ou reformuler les vraies garanties réseau au niveau OS ;
2. **A-02** : compléter le governor machine (RAM agrégée/headroom/heavy-task scheduling) avant multi-session lourd ;
3. **B-01/B-13** : ToolProfiles + compatibilité/sandbox réelle des toolchains avant réadmission ;
4. **A-07** : ApprovalBroker exact et application-owned ;
5. **A-05/B-15/A-09** : modèle read/search handle-first/scopé avant toute recherche PC ;
6. **B-14/A-10/B-12** : env profiles + HardenedCommandRunner commun ;
7. **B-08/B-09/B-10/B-11** : hardening MCP/transport ;
8. **B-16/B-17** : supply-chain/versioning avant release publique ;
9. **A-06/A-12** : renewal + config persistante avant UX produit/multi-session public.

## Conclusion

Les deux audits ont été utiles : les findings les plus dangereux sur la **cohérence lifecycle/process** ont réellement provoqué des changements d'architecture et sont maintenant largement fermés. Le projet ne doit toutefois pas considérer les audits comme entièrement soldés : les points restants sont surtout ceux nécessaires pour passer d'un bridge local prudent à une plateforme d'autonomie durable, multi-session et éventuellement distante.
